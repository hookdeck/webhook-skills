# Setting Up Dots Webhooks

## Prerequisites

- A Dots account with access to the Dots dashboard
- A publicly reachable **HTTPS** endpoint (use the Hookdeck CLI tunnel for local work)

## How Do I Add a Dots Webhook Endpoint?

Dots delivers webhooks through Svix, so you add endpoints in the Svix dashboard:

1. Open the Dots dashboard.
2. From the sidebar, choose the App you want, or open the Organization settings to configure
   organization-level webhooks (these also receive app-originated events, tagged with `api_app_id`).
3. Open the **API Management** tab and follow the link to the Svix dashboard.
4. Click **+ Add Endpoint**.
5. Enter your endpoint URL, e.g. `https://example.com/webhooks/dots`, or use an endpoint
   generated by Svix.
6. Optionally add a description.
7. Select the event types to subscribe to. If you select none, the endpoint receives all
   events. Dots recommends the canonical `.updated` events.
8. Optionally enable a rate limit for the endpoint.
9. Click **Create**, then note the webhook signing secret.

Return an HTTP `2xx` within 15 seconds to acknowledge each event. If your framework enables
CSRF protection by default, disable it for the webhook route.

## Where Do I Find the Signing Secret?

Each endpoint has its own signing secret, shown in the Svix dashboard. Dots' docs don't print
the value or its format; Svix secrets start with `whsec_`. Store the full value:

```bash
DOTS_WEBHOOK_SECRET=whsec_xxxxxxxxxxxxxxxxxxxxxxxx
```

If your secret doesn't start with `whsec_`, the examples reject it at startup with a 500
rather than verifying with the wrong key. Adjust the check if you receive a different format.
A secret from a different endpoint won't verify.

## Testing

No challenge or validation request is sent when you create an endpoint. Trigger a real change
(a flow, transfer, or payout link in your Dots app) or use the Svix dashboard's test-event
option to send a delivery, and watch for it locally with
`npx hookdeck-cli listen 3000 dots --path /webhooks/dots`.
