# Setting Up Modem Pay Webhooks

## Prerequisites

- A Modem Pay business account with dashboard access
- An HTTPS endpoint that accepts `POST` (Modem Pay: "Create a dedicated POST endpoint on your server … accessible over HTTPS")

## Get Your Webhook Secret

"You can generate your unique Modem Pay webhook secret in the Modem Pay dashboard under Developers > Webhooks."

Store it as `MODEM_PAY_WEBHOOK_SECRET` and use it exactly as shown, with no decoding or prefix stripping. It is the HMAC-SHA512 key for `x-modem-signature`.

## Register Your Endpoint

Modem Pay's docs don't spell out where the endpoint URL is entered; the webhook secret lives under Developers > Webhooks, so start there. With the examples in this skill the path is `/webhooks/modem-pay`.

Behind Hookdeck, create a source with the **Modem Pay** source type, enter the same webhook secret, and register the Hookdeck source URL with Modem Pay. Hookdeck's source then verifies `x-modem-signature` on every request and only accepts `POST`.

## Test Mode with the Modem Pay CLI

Modem Pay's CLI forwards test-mode events to a local URL:

```bash
npm install -g modem-pay-cli
modempay login
modempay listen --forward-url=http://localhost:3000/webhooks/modem-pay
# Ready! Your webhook signing secret is '...'
modempay trigger charge.succeeded
```

"For testing purposes, always use the webhook secret generated by the listen command." It is also in the dashboard in test mode only. Live secrets and endpoints aren't affected by test-mode settings, so put the test secret in `MODEM_PAY_WEBHOOK_SECRET` while testing and the live one in production.

`modempay trigger` can send `customer.created`, `customer.updated`, `customer.deleted`, `payment_intent.created`, `payment_intent.cancelled`, `charge.succeeded`, `charge.failed`, `charge.cancelled`, `charge.created` and `charge.updated`.

You can also use the Hookdeck CLI tunnel, with no account needed:

```bash
npx hookdeck-cli listen 3000 modem-pay --path /webhooks/modem-pay
```

## Test Mode vs Live Mode

The documented charge payload carries `test_mode` (`true` in the test-mode sample). Where it's present, check it before fulfilling orders, so a test event can't release goods in production.
