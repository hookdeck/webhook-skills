# Setting Up Mollie Webhooks

## Prerequisites

- A [Mollie](https://www.mollie.com) account
- Your application's publicly reachable webhook endpoint URL

Mollie has two webhook systems (see [overview.md](overview.md)). Classic
webhooks need only your API key. Next-gen webhooks need a webhook subscription
and its signing secret.

## Get Your API Key

Classic webhooks use your regular **API key** for both creating payments and
fetching them in the webhook handler. Classic webhooks have no signing secret.

1. Log in to the [Mollie Dashboard](https://my.mollie.com).
2. Go to **Developers → API keys**.
3. Copy the **Test API key** (`test_…`) for development, or the **Live API key**
   (`live_…`) for production.

Put it in your environment:

```bash
MOLLIE_API_KEY=test_xxxxx
```

Test and live keys are fully separate — a test key only sees test payments.

## Register Your Endpoint (classic)

Classic webhooks have **no dashboard setting**. You set the `webhookUrl` **per
payment** when you create it via the API:

```javascript
const { createMollieClient } = require('@mollie/api-client');
const mollie = createMollieClient({ apiKey: process.env.MOLLIE_API_KEY });

const payment = await mollie.payments.create({
  amount: { currency: 'EUR', value: '10.00' },
  description: 'Order #12345',
  redirectUrl: 'https://example.com/order/12345',
  webhookUrl: 'https://example.com/webhooks/mollie', // ← Mollie will POST here on status change
  metadata: { order_id: '12345' },                   // ← reconcile this in your handler
});

// Redirect the customer to complete payment:
// payment.getCheckoutUrl()
```

Notes:

- The `webhookUrl` **must be publicly reachable** — `localhost` will not work.
  Use a tunnel (see below) during development.
- Some resources (subscriptions, refunds via profiles) also accept a
  `webhookUrl`; the same fetch-to-confirm handler applies.
- There is **no** "select events" step for classic webhooks — Mollie notifies
  you on every status change for that resource.

## Register Your Endpoint (next-gen)

Next-gen webhooks are account-level subscriptions to event types.

1. **Dashboard:** go to **Developers → Webhooks** and create a webhook with your
   URL (e.g. `https://example.com/webhooks/mollie/events`) and the event types you
   want.
2. **API:** `POST https://api.mollie.com/v2/webhooks` with `name`, `url` and
   `eventTypes` (a list, or `*` for all), plus `testmode: true` for a test-mode
   subscription. It needs an access token with the `webhooks.write` permission.

```bash
curl -X POST https://api.mollie.com/v2/webhooks \
  -H "Authorization: Bearer $MOLLIE_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name": "Order events", "url": "https://example.com/webhooks/mollie/events", "eventTypes": ["payment.paid", "payment-link.paid"]}'
```

### The signing secret

Store the subscription's signing secret as `MOLLIE_WEBHOOK_SECRET`. Mollie's
docs are inconsistent about where it comes from: the next-gen guide says to
"generate a secret string" and refers to "the signing secret you provided to
us", while the Create webhook API response includes a `webhookSecret` and the
best-practices page calls it a "shared secret generated by Mollie Webhooks
system". Use the secret your webhook setup shows or returns.

To rotate it, use **Roll secret** in the Dashboard (or the Webhooks API). For the
next 24 hours each event carries two `X-Mollie-Signature` headers, one per
secret, so you can switch secrets without dropping deliveries.

### Next-gen limits

- Live mode requires an HTTPS URL; test mode has no such requirement.
- 2 active subscriptions per organization in test mode, up to 3 in live mode.
- A webhook that keeps failing over 24 hours is marked `blocked` and delivery
  stops until you reactivate it in **Developers → Webhooks**.

## Local Development

Mollie must reach your handler over the public internet. Use the Hookdeck CLI to
tunnel to your local server — no install, no account:

```bash
npx hookdeck-cli listen 3000 mollie --path /webhooks/mollie                # classic
npx hookdeck-cli listen 3000 mollie-events --path /webhooks/mollie/events  # next-gen
```

Use the first public URL as the `webhookUrl` when creating a payment (classic),
and the second as the URL of a test-mode subscription (next-gen).

## Test Mode vs Live Mode

- Use the **test** API key (`test_…`) and create test payments. Mollie's test
  checkout lets you pick the resulting status (paid, failed, expired, etc.), which
  triggers the corresponding webhook call.
- Switch to the **live** API key (`live_…`) for production. The handler code is
  identical — only the key changes.

## Retries

If your endpoint does not return **HTTP 200** within 15 seconds, Mollie retries
the webhook, up to 10 attempts over roughly **26 hours** (both systems). Always
return `200` once you have accepted the call (including for unknown ids); return
a non-200 only when you want Mollie to retry (e.g. the Mollie API was temporarily
unreachable when you tried to fetch the payment).
