# How to Verify Snipcart Webhooks

## There Is No Signature

**Snipcart does not sign webhook payloads.** There is:

- no signature header (there is no `X-Snipcart-Signature` — do not invent one)
- no HMAC of any kind, and nothing to compare timing-safely
- no shared webhook signing secret
- no timestamp header and no replay window

If you find yourself writing `crypto.createHmac` or `hmac.new` for Snipcart,
stop: it is not how this provider works.

## How It Actually Works: Callback Validation

From the webhooks introduction, *Securing your webhook endpoint*:

> "To ensure the authenticity of requests from Snipcart, especially for
> protected data, use the `X-Snipcart-RequestToken` header. This header, added
> to each outbound request, contains a token valid for one hour. You can verify
> this token by making a `GET` request to
> `https://app.snipcart.com/api/requestvalidation/{token}`, functioning as a
> form of digital handshake."

From [Validating the request token](https://docs.snipcart.com/v3/setup/order-validation):

> "`X-Snipcart-RequestToken` is a random token generated by our servers. To
> confirm that a request really came from Snipcart, call our API with it,
> authenticated with your secret API key: `GET
> https://app.snipcart.com/api/requestvalidation/{token}`. A `200` means the
> token is genuine. The response body also carries the resource we asked for,
> so you can check it against the URL that was hit. A `404` means the token is
> unknown, already validated, or expired." … "The same header is sent with
> webhook requests."

So the trust model is a **callback**: the payload proves nothing on its own, and
the proof is an authenticated round-trip to Snipcart.

## Authenticating the Validation Call

From [API authentication](https://docs.snipcart.com/v3/api-reference/authentication):

> "Snipcart's REST API uses the HTTP Basic authentication scheme." … "Pass the
> API key as the username, with no password. … if your key is `secret`, you
> base64-encode `secret:` — the trailing colon is important."

```
Authorization: Basic <base64(SNIPCART_SECRET_API_KEY + ":")>
Accept: application/json
```

The docs call the trailing colon "important": `base64("key")` and
`base64("key:")` are different strings, and only the second is the documented
credential format.

## The Algorithm, Step by Step

1. **Read the header** `X-Snipcart-RequestToken`. Header names are
   case-insensitive; Node lowercases to `x-snipcart-requesttoken`, and it has
   been seen on the wire as `X-Snipcart-Requesttoken`. Missing or empty →
   reject `401`, **without** calling Snipcart.

2. **Format-check the token before it touches the URL.** The token is
   attacker-controlled input that you are about to interpolate into the path of
   a request carrying your **secret key**. Observed tokens are UUIDs, e.g.
   `252e5ce5-7450-4ab4-bcda-57f1e7f6a51d`. Accept only:

   ```
   /^[A-Za-z0-9_-]{1,128}$/     (after trimming)
   ```

   `encodeURIComponent` is **not** sufficient here: it leaves `.` and `..`
   intact, and the URL parser resolves them as dot segments — a token of `..`
   turns your request into `GET https://app.snipcart.com/api/`, whose `200`
   would be misread as "the token is genuine". Reject anything else outright.

3. **Call the endpoint:**

   ```
   GET https://app.snipcart.com/api/requestvalidation/{token}
   Authorization: Basic <base64(secretKey + ":")>
   Accept: application/json
   ```

   - **Do not follow redirects** (`redirect: 'manual'` in `fetch`,
     `follow_redirects=False` in `httpx`). Never forward the secret key to
     wherever a redirect points, and only a *direct* 200 should count.
   - Use a timeout around **5 seconds** (`AbortSignal.timeout(5000)` /
     `httpx.AsyncClient(timeout=5)`).

4. **Interpret the status:**

   | Status | Meaning | Do |
   |--------|---------|-----|
   | `200` | Token is genuine | Accept, then parse the body |
   | `404` | Unknown, already validated, or expired | Reject `401` |
   | `401` / `403` | Not defined in the docs; a Snipcart support answer attributes `401` to a missing secret key, and a wrong or other-mode key is the likely cause | Reject `401`, alert yourself — probably a config bug |
   | anything else / network error / timeout | Unknown | **Fail closed** — reject |

   Never treat a `5xx` as success. Log upstream failures **without** logging the
   key or the token.

5. **Only after a 200**, `JSON.parse` the raw body and dispatch on `eventName`.

## Optional: Check the Resource (Defense in Depth)

The docs say the 200 response body "carries the resource we asked for" but do
not specify its shape. Community implementations read two fields:

- `token` — the FosterCommerce Craft plugin compares it back to the header token
- `resource` — Snipcart's WordPress demo checks that it contains its own
  endpoint path

Both field names are **community-observed, not documented**. Treat a `resource`
check as an optional extra layer; do **not** make your verifier depend on body
fields. The documented signal is the status code.

## Unset Key: Fail Closed, Loudly

If `SNIPCART_SECRET_API_KEY` is missing, the verifier must raise a clear
**configuration error** and the endpoint must return `500` — never skip
validation and never accept the request. A receiver that silently accepts
everything when the key is absent is an open endpoint.

## Token Lifetime and One-Time Use

- Webhook tokens are **valid for one hour**. Validate **synchronously at
  receipt**, not later from a queue that might sit longer than that.
- The endpoint documents `404` as "unknown, **already validated**, or expired",
  and the order-validation page states for crawler requests that "the token can
  be validated once. A second call returns 404." Whether *webhook* tokens are
  single-use is not stated explicitly — assume they are, and validate each token
  **exactly once**.
- Consequence with a gateway in front: if Hookdeck's `SNIPCART` source type has
  already validated the token at ingestion, your destination must **not**
  re-validate it. Rely on Hookdeck's verification and check the
  `x-hookdeck-signature` header at the destination instead.
- The dashboard's **"Send this hook again"** button re-sends the request. The
  docs say the token header is "added to each outbound request", so a resend
  should carry its own token — not stated verbatim for resends, so verify
  against the dashboard's request log if a resend behaves oddly.

## Testability

Because verification is a **network call**, make it injectable or mockable:

- **Express / Next.js** — the examples call global `fetch` (Node 18+, no
  dependency). Tests stub it with `jest.spyOn(globalThis, 'fetch')` /
  `vi.spyOn(globalThis, 'fetch')`.
- **FastAPI** — the example uses `httpx` (already a FastAPI test dependency).
  Tests inject an `httpx.MockTransport`, so no extra package (`respx`, etc.) is
  needed.

There is **no official Snipcart SDK for webhook validation** — do not reference
one. The examples use only Node built-ins and `httpx`.

What your tests should assert:

| Case | Expected |
|------|----------|
| Snipcart returns `200` | Request accepted, `200` + JSON body |
| Snipcart returns `404` | `401` |
| Snipcart returns `401` | `401` |
| Missing `X-Snipcart-RequestToken` | `401`, and **no** outbound call |
| Token `..`, `../orders`, or `a/b` | `401`, and **no** outbound call |
| Network error / timeout | `401` (fail closed) |
| Outbound request shape | exact URL, `GET`, `Authorization: Basic base64(key + ":")`, redirects not followed |
| `SNIPCART_SECRET_API_KEY` unset | `500` |

## Responding

Snipcart requires `Content-Type: application/json` **and** status `200`:

```json
{ "received": true }
```

Return `400` for an unparsable body or a missing `eventName`; `401` for a
failed token validation; `500` for a missing key.

## Common Gotchas

- **Looking for a signature header.** There isn't one. Verification is the
  callback.
- **Using the public API key.** Snipcart's REST API authenticates with a
  **secret** key; the public key belongs in the front-end snippet only.
- **Forgetting the trailing colon** in `base64(key + ":")` → `401` from Snipcart.
- **Mode mismatch.** A Test-mode key cannot read Live data (and vice versa); a
  mismatched key is a plausible cause of a `401`/`403` from `requestvalidation`.
- **Validating from a background job.** The token expires in an hour and is
  likely single-use.
- **Validating twice** (e.g. a gateway and your app both doing it) → if webhook
  tokens are single-use like crawler tokens, the second call gets `404`.
- **Following redirects**, which risks leaking the secret key.
- **Failing open** on a timeout or 5xx. Always reject.
- **Strict schema validation.** Snipcart adds payload fields without notice —
  ignore unknown fields.
- **Sending `shippingrates.fetch` / `taxes.calculate` through a gateway.** Their
  response body is consumed at checkout; point them straight at your app.
